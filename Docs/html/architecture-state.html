Overview

All six apps follow MVVM using Jetpack ViewModel + Kotlin StateFlow. The differences lie in how complex the state model is, how many flows are combined, and whether a domain (UseCase) layer sits between repository and ViewModel.

App UiState style Flow complexity Domain layer DI
JetLagged data class (static) None — no flows No No
Reply data class + .copy() Single flow (emails) No No
JetNews sealed interface (NoPosts / HasPosts) 2 flows combined No Manual factory
Jetchat Simple data class SharedFlow for events No No
Jetsnack Local state + StateFlow per screen Medium No No
Jetcaster @Immutable data class + sealed interface actions 7 flows combined Yes (UseCases) Hilt

The Core Pattern (All Apps)

Every app follows the same 4-step data flow. The key rule: composables never own business logic. They observe state and fire events upward.

Repository / Data source
    ↓  (Flow / suspend fun)
ViewModel
    ↓  (StateFlow<UiState>)
collectAsStateWithLifecycle()
    ↓  (State<UiState>)
Composable (renders UI)
    ↓  (user event / callback)
ViewModel event handler
    ↓  (updates MutableStateFlow)
[cycle repeats]

UiState Modelling Patterns

Four patterns from simplest to most structured — pick based on screen complexity.

Pattern 1 — Static data class (JetLagged)

No repository, no flow collection. State is created once and never changes. Good baseline before complexity is added.

Kotlin 
// JetLaggedHomeScreenViewModel.kt
class JetLaggedHomeScreenViewModel : ViewModel() {
    val uiState: StateFlow<JetLaggedHomeScreenState> =
        MutableStateFlow(JetLaggedHomeScreenState())
}

Pattern 2 — Mutable data class with .copy() (Reply)

All screen states share the same fields (loading, error, data co-exist on the same class). Updates are immutable via .copy().

Kotlin 
// ReplyHomeViewModel.kt
private val _uiState = MutableStateFlow(ReplyHomeUIState(loading = true))
val uiState: StateFlow<ReplyHomeUIState> = _uiState

data class ReplyHomeUIState(
    val emails: List<Email> = emptyList(),
    val selectedEmails: Set<Long> = emptySet(),
    val openedEmail: Email? = null,
    val isDetailOnlyOpen: Boolean = false,
    val loading: Boolean = false,
    val error: String? = null,
)

// State updates via .copy()
fun setOpenedEmail(emailId: Long, contentType: ReplyContentType) {
    val email = uiState.value.emails.find { it.id == emailId }
    _uiState.value = _uiState.value.copy(
        openedEmail = email,
        isDetailOnlyOpen = contentType == ReplyContentType.SINGLE_PANE,
    )
}
When to use

When all screen states share the same fields — loading, error, and data all co-exist on the same class.

Pattern 3 — Internal state → public sealed UiState (JetNews)

Separates internal raw state from the public typed state exposed to the UI. The HasPosts type guarantees postsFeed is non-null at compile time.

Kotlin 
// Internal — raw, mutable, easy to update
private data class HomeViewModelState(
    val postsFeed: PostsFeed? = null,
    val favorites: Set<String> = emptySet(),
    val isLoading: Boolean = false,
    val errorMessages: List<ErrorMessage> = emptyList(),
    val searchInput: String = "",
) {
    fun toUiState(): HomeUiState = if (postsFeed == null) {
        HomeUiState.NoPosts(isLoading, errorMessages, searchInput)
    } else {
        HomeUiState.HasPosts(postsFeed, favorites, isLoading, errorMessages, searchInput)
    }
}

// Public — sealed, UI exhausts all cases with when()
sealed interface HomeUiState {
    val isLoading: Boolean
    val errorMessages: List<ErrorMessage>
    val searchInput: String

    data class NoPosts(
        override val isLoading: Boolean,
        override val errorMessages: List<ErrorMessage>,
        override val searchInput: String,
    ) : HomeUiState

    data class HasPosts(
        val postsFeed: PostsFeed,          // non-null guaranteed here
        val favorites: Set<String>,
        override val isLoading: Boolean,
        override val errorMessages: List<ErrorMessage>,
        override val searchInput: String,
    ) : HomeUiState
}

// Exposed via stateIn
val uiState = viewModelState
    .map(HomeViewModelState::toUiState)
    .stateIn(viewModelScope, SharingStarted.Eagerly, viewModelState.value.toUiState())
Why this pattern

HasPosts guarantees postsFeed is non-null at compile time. No postsFeed?.let { } defensive coding needed in composables.

Pattern 4 — @Immutable + sealed Action interface (Jetcaster)

The most structured approach. @Immutable tells the Compose compiler to skip recomposition when the state reference hasn't changed. All user events funnel through a single onAction dispatch function.

Kotlin 
@Immutable
data class HomeScreenUiState(
    val isLoading: Boolean = true,
    val errorMessage: String? = null,
    val featuredPodcasts: ImmutableList<PodcastInfo> = persistentListOf(),
    val selectedHomeCategory: HomeCategory = HomeCategory.Discover,
    val homeCategories: List<HomeCategory> = emptyList(),
)

// All user events as sealed interface — one entry point
@Immutable
sealed interface HomeAction {
    data class CategorySelected(val category: CategoryInfo) : HomeAction
    data class HomeCategorySelected(val category: HomeCategory) : HomeAction
    data class TogglePodcastFollowed(val podcast: PodcastInfo) : HomeAction
    data class QueueEpisode(val episode: PlayerEpisode) : HomeAction
}

// Single dispatch function
fun onHomeAction(action: HomeAction) {
    when (action) {
        is HomeAction.CategorySelected     -> onCategorySelected(action.category)
        is HomeAction.HomeCategorySelected -> onHomeCategorySelected(action.category)
        is HomeAction.QueueEpisode         -> onQueueEpisode(action.episode)
        // ...
    }
}

// In composable — single callback
MyScreenContent(
    uiState = uiState,
    onAction = viewModel::onHomeAction,
)

@Immutable

Tells the Compose compiler it can skip recomposition when the state reference hasn't changed. Without it, the compiler conservatively recomposes on every emission.

ImmutableList

Standard List<T> is not stable in Compose's eyes (it's an interface). ImmutableList has a stable contract — no surprise recompositions.

Flow Combination (Jetcaster)

Jetcaster's ViewModel combines 7 StateFlows into a single UiState using a custom combine utility. This is the most complex pattern in the repo.

Kotlin — HomeViewModel.kt 
combine(
    homeCategories,                                                         // Flow 1: available tabs
    selectedHomeCategory,                                                   // Flow 2: selected tab
    subscribedPodcasts,                                                     // Flow 3: followed podcasts
    refreshing,                                                             // Flow 4: loading indicator
    _selectedCategory.flatMapLatest { filterableCategoriesUseCase(it) },   // Flow 5
    _selectedCategory.flatMapLatest { podcastCategoryFilterUseCase(it) },  // Flow 6
    subscribedPodcasts.flatMapLatest { podcasts ->
        episodeStore.episodesInPodcasts(podcasts.map { it.podcast.uri }, 20)
    },                                                                      // Flow 7: library
) { homeCategories, homeCategory, podcasts, refreshing,
    filterableCategories, podcastCategoryFilterResult, libraryEpisodes ->

    HomeScreenUiState(
        isLoading = refreshing,
        featuredPodcasts = podcasts.map { it.asExternalModel() }.toPersistentList(),
        // ...
    )
}.catch { throwable ->
    emit(HomeScreenUiState(isLoading = false, errorMessage = throwable.message))
}.collect {
    _state.value = it
}

flatMapLatest

When the selected category changes, cancel the previous inner flow and start a new one. Prevents stale data from an old selection.

.catch { }

Error recovery at the combine level. Converts any exception into an error UiState without crashing the entire flow.

Repository Pattern

Repository hides the data source. ViewModel doesn't know if data comes from a database, network, or static list.

Simple (Reply)

Kotlin 
// Interface
interface EmailsRepository {
    fun getAllEmails(): Flow<List<Email>>
}

// Implementation — swap out without changing ViewModel
class EmailsRepositoryImpl : EmailsRepository {
    override fun getAllEmails(): Flow<List<Email>> = flow {
        emit(LocalEmailsDataProvider.allEmails)
    }
}

Layered with UseCases (Jetcaster)

UseCases let you unit-test transformation logic independently and reuse the same data-fetching logic in multiple ViewModels (mobile + TV share the same UseCase).

Kotlin 
class FilterableCategoriesUseCase @Inject constructor(
    private val categoryStore: CategoryStore,
    private val podcastStore: PodcastStore,
) {
    operator fun invoke(selectedCategory: CategoryInfo?): Flow<FilterableCategoriesModel> =
        combine(
            categoryStore.categoriesSortedByPodcastCount(),
            podcastStore.followedPodcastsSortedByLastEpisode(),
        ) { categories, podcasts -> /* transform */ }
}

Consuming State in Composables

The correct way to collect flows in composables — lifecycle-aware, no background leaks.

Kotlin 
// ✅ Stops collecting when composable is not visible (lifecycle below STARTED)
val uiState by viewModel.uiState.collectAsStateWithLifecycle()

// Side effects
LaunchedEffect(key1 = errorMessage) {
    if (errorMessage != null) {
        snackbarHostState.showSnackbar(errorMessage)
        viewModel.errorShown(errorMessage.id)
    }
}

SideEffect {
    systemUiController.setSystemBarsColor(color = backgroundColor)
}
Rule

Never launch coroutines inside @Composable functions directly. Use LaunchedEffect or rememberCoroutineScope.

Key Rules at a Glance

Question Answer
How many ViewModels per screen? One ViewModel per screen — never shared across screens
How is state exposed? Always StateFlow<UiState> — never raw MutableStateFlow public
How does UI send events? Via callback lambdas or a sealed Action interface
How is error handled? As a field inside UiState (error: String?) — not thrown in composables
When does collection stop? collectAsStateWithLifecycle() stops at STARTED — no background leaks
How are multiple flows merged? combine() / flatMapLatest() inside viewModelScope.launch {}

Which Pattern to Use

Decision guide — start from top and stop at the first match.

Is your screen data static / one-time?
    YES → Simple MutableStateFlow(initialState) — no collection (JetLagged)

Do all states share the same fields (loading + data + error together)?
    YES → data class UiState + .copy() updates (Reply)

Are some fields only valid in certain states?
    YES → sealed interface UiState — HasPosts guarantees non-null (JetNews)

Do you have many user events going to one ViewModel?
    YES → sealed interface Action + single dispatch (Jetcaster)

Do you need to combine 3+ independent data sources?
    YES → combine() + flatMapLatest() inside viewModelScope (Jetcaster)

Do you share logic across multiple ViewModels (mobile + TV)?
    YES → Extract to UseCase (Jetcaster's FilterableCategoriesUseCase)
